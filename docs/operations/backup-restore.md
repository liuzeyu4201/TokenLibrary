# 备份、保留期与隔离恢复

更新：2026-09-26。实现：`server/internal/jobs/`、`server/cmd/library-admin/`。验证记录见 [备份与部署验收](../testing/backup-validation.md)。

## 每日联合备份

调度器每 30 秒检查。默认每天北京时间 03:00；启动时补最近一个应执行的计划，不连补每个停机日。失败按 15 分钟、60 分钟重试，同一计划最多 3 次。备份目录到期清理有独立循环，不依赖新备份成功。

1. 设置 maintenance，拒绝新云端写入，然后最多等待 60 秒取得进程独占写门闩。正在执行的上传、发布、同步事务排空；全程默认上限 20 分钟。
2. 清理已到期回收站、上传临时数据及过期备份。任何专属文件清理失败都使本轮备份失败。
3. 在暂停文档写入的窗口，使用与 PG 主版本一致的 `pg_dump --format=custom` 导出数据库；复制当前、历史、冲突、批注仍引用的 ready 附件。完成但未关联文档的上传不作为可恢复文档复制。
4. 逐文件校验大小/SHA-256，检查 `pg_restore --list`。manifest 记录库 ID、epoch、结构摘要、PG 主版本、快照/到期时间、最早回收站到期时间和文件清单；文件与目录持久写入后原子改名为 UUID 目录，才记录成功。
5. 发布前若有回收站项目跨过到期时刻，备份作废；不会发布当时已过期内容。异常、取消、复制/dump 失败、超时均等待子进程结束、删除临时结果、解除维护。进程重启将遗留运行任务标为中断并解除该备份造成的维护。

成功目录结构：

```text
BACKUP_ROOT/<backup UUID>/
  db.dump
  manifest.json
  manifest.sha256
  files/<UUID 前两位>/<blob UUID>
```

文件是独立副本，不用硬链接。备份盘低于 1 GiB 可用空间拒绝开始；实际所需容量仍取决于全库大小。应预留活动数据、7 份完整备份、临时备份及校验余量，不能把 1 GiB 门槛当容量保证。`pg_dump` 自身只保证数据库快照；暂停应用写入使其与附件集合协调一致。[PostgreSQL pg_dump](https://www.postgresql.org/docs/current/app-pgdump.html)

## 期限与失败状态

- 备份在 `snapshotAt + 7×24h` 到期。恢复工具实时拒绝到期结果；后台先标记过期再删除目录。新备份失败也继续删过期备份，不能无限保留最后一份。崩溃遗留 `.partial-*` 不可恢复，最长 7 天后清理。
- 回收站以服务器记录的 `purgeAt` 到期（正常删除后 30 天）。清理当前正文、修订、冲突草稿、冻结快照、操作回执及历史 change 中的正文，保留只有 UUID 等必要字段的墓碑；每个删除事件使用独立序号。
- 专属无引用原件立即物理清理；仍被其他资料引用的共享 blob 保留。普通未关联上传有 24 小时宽限，有效上传租期也保护文件；一个过期上传不会删除同一 blob 的新有效会话。
- 删除失败写日志并保留可重试状态。停机或磁盘故障无法保证机器当时执行删除，恢复运行后追补；这不是磁盘取证级擦除，也无法撤回离线设备或用户另行导出的副本。

数据库记录备份任务及错误摘要；诊断时只查询状态/时间/错误，不输出正文、凭据或完整连接串。`jobs` 的 failed 不等于存在可恢复目录；`backups.state=success`、未到期、完整校验通过才有资格恢复。校验清单不等于完成过真实恢复演练。

## 恢复流程

恢复是服务器管理员的显式操作。工具只接受**空数据库和空数据目录**，不会覆盖活动库，也没有自动恢复 HTTP 接口。先验证新目标，再决定切换配置；失败时保留原库和原文件，隔离失败目标不得直接用于 service。

1. 选定未过期的 UUID 备份目录。保留实际 `.env`、账号设置和 Caddy 证书配置；业务备份不会替换这些秘密。
2. 使用与备份 PG 主版本相同的 PostgreSQL 创建一个空数据库（例如 `tokenlibrary_restored`，名称由管理员选择），以及独立空文档目录。为 app UID/GID 准备写入权限。先在旧服务仍可回退的情况下隔离恢复；正式切换前停止本项目 app，避免切换期间继续产生未包含在恢复点中的写入。
3. 在包含 `library-admin`、同版本 `pg_restore` 和当前 schema 的运行环境中挂载备份目录、新文档目录。通过受限环境文件/管理终端设置 `RESTORE_DATABASE_URL` 指向空目标库，设置 `BACKUP_ROOT` 为备份根；不要把 URL 密码写在命令参数或历史中。工具命令如下（替换路径和 UUID）：

```sh
library-admin verify --backup /backup/BACKUP_UUID
library-admin restore --backup /backup/BACKUP_UUID --data-root /restored --schema /app/schema/initial.sql
```

工具实时校验期限、路径、清单及所有哈希；拒绝符号链接、路径逃逸、未发布目录、结构摘要或 PG 主版本不符。`pg_restore --exit-on-error --single-transaction` 恢复数据库，复制并再次验证原件及所有引用。保持 `libraryId`，生成全新 `epoch`，撤销旧会话、旧上传、操作去重记录、分页快照及调度记录；删除未纳入备份的无引用 blob 行，避免把没有原件的旧上传误认为已完成。恢复后再按当前时间清理到期数据，最后解除维护。[PostgreSQL pg_restore](https://www.postgresql.org/docs/current/app-pgrestore.html)

4. 检查恢复库的正文、书目元数据、专题、冲突材料、PDF/图片原件和 hash；确认库 ID 相同、epoch 不同、维护已关闭。完整媒体场景测试使用实际样本，不以目录存在判断成功。
5. 切换 `.env` 中 `POSTGRES_DB` 到恢复的新库，`DATA_ROOT` 到新文档目录。**如果继续使用原 PostgreSQL 集群，先把 `POSTGRES_DATA_ROOT` 固定到原集群的绝对路径；不能随 DATA_ROOT 切换而意外挂载一个空 PG 目录。** 若 Caddy 证书原来在旧 DATA_ROOT/caddy，切换前由管理员保留并迁移该配置，或安排重新签发；不要混入文档备份。
6. 用既有 `make start` 重建 service，验证 ready 与 HTTPS。两端重新登录。新 epoch 会使旧队列停止重放；客户端应展示恢复后的差异供用户处理，而不是静默丢弃晚于备份的本机修改。确认无误后再按管理员的回退窗口处理旧活动库，工具不会代删它。

`verify` 仅检查封装完整性；没有签名认证保证。能修改备份与 checksum 的管理员也能修改备份内容，故备份目录权限与独立存储仍重要。真实恢复已在隔离 PG17 容器和 PG18 临时集群验证；尚未拿实际用户库执行切换或演练公网证书续期。
