# 编辑并发与恢复草稿

更新：2026-09-26。

## 保存边界

`DocumentStore.saveMarkdownEdit(id:baseMarkdown:proposedMarkdown:)` 在同一个 SQLite 写事务中读取最新正文、三方合并、保存正文、更新全文索引和待同步队列。独立行修改可合并，包括同一方同时修改多段；同一行或同一插入位置的竞争修改会保守地保留草稿，不向正文写入冲突标记。

对大规模全文替换，差异窗口超过 8192 行时使用单个保守修改区间，避免通用差异算法的最坏情况占用过长时间。无法安全合并时仍保存完整草稿，而不是丢弃较大修改。

`MarkdownEditSession` 固定绑定创建时的 `DocumentStore` 和资料 ID。界面切换服务器或资料库后，旧编辑器的最后输入仍保存到原资料库。`save(_:)` 使用上次成功保存后的正文作为基线；异步编辑器应调用 `save(baseMarkdown:proposedMarkdown:)`，传入这次实际编辑所基于的文本，不能把“宿主刚收到的最新正文”误当成用户的编辑基线。

每个会话拥有固定的草稿 ID，重复冲突更新同一份草稿。返回 `.conflict(markdown:conflictID:)` 中的 `markdown` 是当前权威正文，用户提议的内容则保存在草稿中。调用方应明确提示冲突，并允许恢复草稿。保存失败抛出错误，不能报告“已保存”。

## 删除与恢复

迁移 `v10-editor-drafts` 增加独立草稿表，故意不对资料行设置级联删除。资料回收、到期清理或远端墓碑都不能清除已保存草稿。一个资料可能为待处理同步冲突而仍保留本机工作行；保存接口同时检查远端墓碑，避免把这类保留行误认为仍可编辑的远端资料。

`editorDrafts(documentId:)` 读取恢复材料，`discardEditorDraft(id:)` 明确放弃草稿，`recoverEditorDraftAsCopy(id:parentId:)` 在有效文件夹内创建新 ID 的副本。原资料的正文、回收状态和墓碑保持不变。副本与草稿删除一起提交；失败则保留草稿。副本保留 Markdown 相对附件引用、原始元数据以及 PDF 的原版本位置，名称自动避让。

## PDF 批注

`savePDFAnnotationEdit(id:expectedPDFBlobId:expectedPDFPath:base:proposed:)` 同时核对 PDF blob ID 和本机文件位置，再按批注 ID 三方合并新增、修改和删除。独立批注可合并；同一批注竞争修改、删除对修改、PDF 换版和资料删除会先持久化草稿，再抛出含恢复指引的 `EditorEditError`。

PDF 草稿恢复使用原 PDF 的位置和 blob ID，绝不把旧页码坐标应用到新版本。若原文件缺失，恢复操作明确失败并保留草稿。附件文件本身仍采用资料库现有的不可变媒体文件，不因创建恢复副本重复复制大文件。

## 层级解析

`LibraryHierarchy.rootID(for:documents:localRootID:)` 停在服务器真实根目录自身，兼容默认 `root` 的本机虚拟根。缺失父目录、环路、重复 ID 或把文件当父目录会返回 `nil`。根目录 ID 不会被错误地解析成空字符串。

`bindWorkspace(server:libraryId:rootId:)` 可持久化经过认证的根 ID，首次快照尚未完成时允许该 ID 作为虚拟根。同步入口使用已认证会话的根 ID，不根据任意缺父资料推断身份。改名和移动直接在写事务中校验当前资料、有效父级、同库、环路、根保护、专题目标及名称碰撞；名称与服务端一致使用 NFC、大小写折叠和 240 字节上限。原有只更新正文、追加批注接口也在事务内读取当前行，避免结构修改被旧快照覆盖；交互式编辑器仍应使用带基线/身份的新接口。

`createDocument(_:deduplicateName:)` 同样在写事务中校验最新父级及全部祖先。即使界面仍显示已被另一流程删除的旧文件夹，也不会在其中新建孤儿。专题不作为物理容器；新 ID 不能覆盖现存资料或重用墓碑、远端快照、历史队列中的 ID。默认同名自动追加 `_n`，以 UTF-8 字节数截短基名，保留扩展名。新建记录、全文索引和创建操作一起提交；并发创建会依次取得不同名称。
