# 个人资料库的官方产品参考研究

研究与访问日期：2026-09-26  
用途：为 TokenLibrary 的书籍、论文、笔记设计提供有依据的取舍；对应[个人图书馆与档案馆设计](../product/personal-library-archive.md)。  
方法：阅读四个产品的官方帮助或官方产品文章，仅记录页面明确支持的行为；没有进行安装实测、性能比较、同步可靠性比较或价格评估。

## 1. 研究问题

1. 一份论文/一本书应该等同于一个 PDF 文件吗？
2. 同一资料如何服务多个研究问题，又不复制文件？
3. 摘录如何回到原文，笔记如何持续关联资料？
4. “长期保存”如何保持可找回与可导出，而不增加过重的管理负担？

下文“官方事实”来自引用页面，“项目取舍”是针对 TokenLibrary 的设计判断。其他产品的能力不等于本项目已具备该能力。

## 2. Zotero：文献身份、集合与来源定位

**官方事实。** Zotero 区分文献条目、附件和笔记；导入 PDF 后可以补建文献条目，也允许手工录入。它支持 DOI/ISBN 等标识符录入，以及 BibTeX/RIS 等书目数据导入路径。自动取得的信息仍需核对。[Adding Items to Zotero](https://www.zotero.org/support/adding_items_to_zotero)

同一条目可以进入多个集合，添加集合归属不复制条目；集合适合组织项目和主题，标签承担其他描述。[Collections and Tags](https://www.zotero.org/support/collections_and_tags)

阅读批注可加入笔记，并保留返回 PDF 页面的方法；批注存于数据库，外部阅读器要看到批注需要导出嵌入批注的文件。[PDF Reader and Note Editor](https://www.zotero.org/support/pdf_reader)

条目之间可以建立对称相关关系，但关系不传递。[Related Items](https://www.zotero.org/support/related)

**项目取舍。** TokenLibrary 应优先借鉴“条目—原件—摘录—笔记”的连接，以及一项资料归属多个专题的方式。元数据缺失必须允许先阅读，用户不应为添加一份 PDF 被迫填表。引用与相关关系分开，引用保留方向，相关关系双向展示。先解决原文定位和可导出引用说明，再评价完整参考文献排版；浏览器采集、Word 引文插件和复杂文献类型体系不作为当前必需范围。

## 3. calibre：一本书可以有多份文件

**官方事实。** calibre 的一个书籍条目能够管理多个格式；其元数据编辑包含书名、作者等信息，并允许管理关联文件。[Editing e-book metadata](https://manual.calibre-ebook.com/metadata.html)

虚拟书库是原书库按条件限定的子集，用户可以回到全库查询，而不必把资料拆成互不相通的独立库。[Virtual libraries](https://manual.calibre-ebook.com/virtual_libraries.html)

**项目取舍。** 将“书是什么”和“文件是什么格式”分开，避免未来出现 PDF、EPUB 就在书架重复成两本书。书架、论文库和归档使用同库视图；保存搜索可作为后续功能，先做明确的类型/作者/阅读状态筛选。当前只要把 PDF 书籍体验做好就能验证该模型，不因此引入格式转换、电子阅读器设备管理或 EPUB 阅读器工程。不同版次、译本不能仅凭标题合成同一条目。

## 4. Obsidian：自己的文字与可返回的关联

**官方事实。** Obsidian 支持 Markdown 格式内部链接和 Wikilink，可以链接到文件、标题及其特定块；官方文档也说明块引用并非标准 Markdown，在外部工具的兼容性有限。[Internal links](https://obsidian.md/help/links)

Backlinks 显示哪些笔记链接到当前笔记，帮助从被引用项回到上下文。[Backlinks](https://obsidian.md/help/plugins/backlinks)

Properties 用结构化字段描述笔记，并提供文字、列表、日期等类型；文件内以 YAML 保存。[Properties](https://obsidian.md/help/properties)

**项目取舍。** 保留 Markdown 作为可带走的正文；给资料和笔记显示“引用我的笔记”。连接由稳定 ID 支撑，不让改名或移动使链接失效。元数据在应用里提供简单表单，不要求使用者编写 YAML。导出应带可读标题、页码、相对文件链接和关系清单，不能依赖仅在 TokenLibrary 可解读的私有定位 URI。暂不引入图谱、插件依赖或全套 Wikilink 语法，先完成双端一致的链接与来源返回。

## 5. DEVONthink：多处组织与独立副本须区分

**官方事实。** 官方文章区分可以独立编辑的 duplicate 与指向同一项目、共享修改的 replicant；后者用于同一材料出现在多个组织位置。文章发表于 2023-05-24，并明确提醒来自较早产品代际，因此这里只使用数据概念，不照搬菜单与操作路径。[How to Use Duplicates and Replicants](https://www.devontechnologies.com/blog/20230524-duplicates-replicants)

**项目取舍。** 在 TokenLibrary 中用易懂的“加入专题”表达多处使用，用“创建副本”表达独立内容；两项命令不能混用。删除专题成员关系不应该删掉原件。研究归档采用同库的归档状态，不搬运至另一份数据库。本文未验证 DEVONthink 当前版本的备份、OCR、同步或档案合规能力，也不据此作比较判断。

## 6. 收敛为 TokenLibrary 的选择

| 设计问题 | 采用的建议 | 暂缓或不采用的复杂度 | 对实现的要求 |
| --- | --- | --- | --- |
| 资料与文件 | 书籍/论文条目关联文件，笔记保持 Markdown | 完整编目体系、自动版本合并 | 原文档 ID 保留；资料类型不与 PDF/MD 格式混用 |
| 多维组织 | 单库、类型视图、多专题归属、少量标签 | 多数据库、复杂自动分类规则 | 专题关系可单独同步和删除，不复制资料 |
| 阅读与思考 | 摘录保留来源，加入笔记后可回原文 | 自动摘要、AI 结论、巨型关系图 | 页码与文件版本绑定，引用和评论分开 |
| 长期保存 | 原件字节、来源记录、可逆归档、独立备份、可导出正文 | 不可篡改存证、自动历史恢复 | 归档、删除、同步完成、备份完成四种语义分开 |
| 书目输入 | 先手工少量字段，可选联网补全 | 无预览的自动覆盖 | 信息来源可见，补全失败仍能继续阅读 |
| 新格式 | 按真实 EPUB/BibTeX/RIS 样本评估 | 为“像某产品”一次堆入所有格式 | 导入、阅读、定位、同步、导出逐项验收 |
| 移动端 | 继续阅读、摘录、短笔记、明确同步状态 | 复制桌面全部列和面板 | iPhone 能完成同一流程，只改变信息呈现方式 |

优先做稳现有基础，再实施资料组织与研究闭环，是由当前项目的功能缺口决定的工程顺序。四个参考产品没有提供本项目同步可靠性的证据；连接失败、重试、文件传输和数据收敛必须在本项目内独立测试。

## 7. 仍需要项目内验证的假设

- 用户的“书籍”是否主要为 PDF，还是 EPUB 占比较高；这决定新增阅读器的价值与成本。
- “论文库”是否需要迁入已有 Zotero 数据，还是目前以散落 PDF 为主；这决定 BibTeX/RIS 的优先级。
- 是否存在从笔记输出正式论文/文章的习惯；没有这一场景就先不实现复杂引文样式。
- 1000 项规模中的文件体积与手机可用空间；本次研究不据此擅自改变既有全库本地副本默认设计。
- 标题与作者质量参差不齐时，用户能否在几十秒内完成收件箱整理；需要真实样本和两端试用。

这些是后续验证事项，不阻止现有同步和功能缺口修复，也不应被当成已经确认的新增必需范围。
